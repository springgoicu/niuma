# ADR-0009：准入与排队放在游戏进程内，由实测出口带宽驱动闸门

- 状态：已采纳，**容量推导由 [ADR-0043](0043-idle-dirty-and-compact-sync.md) 修订**
- 日期：2026-10-30

## 背景

产品是「零持久化、单进程、进程内存即真相」的多人在线园区，部署在 2C2G / 3Mbps 的单机上。

3Mbps 出网约 375 KB/s，扣掉 TCP/TLS 开销后按 320 KB/s 预算。而单个客户端的下行由协议直接决定：

```
每 Tick（20Hz）包长 = SYNC_HEADER_BYTES(7) + SYNC_ENTRY_BYTES(7) × 视野内实体数
```

也就是说成本不是「在线人数」，而是「观察者 × 可见实体」的对数：同屏走动 50 人就打满，分散挂机 150 人才打满。原有实现只在 `world.create` 返回 null 时 `ws.close(1013, 'server full')`——没有水位、没有排队、没有放行节奏，越限时用户看到的是莫名其妙的断线。

> **2026-11-11 修订（ADR-0043）**：上式里的「视野内实体数」原先等于「视野内所有在线人数」——
> 客户端 20Hz 空发、服务端无条件置 dirty，坐着不动与走来走去同价。改成变化驱动后，
> 条目只来自**真正在动的人**，式中的 N 变成「视野内正在变化的实体数」；同时单条增量
> 由 7 字节压到 6 字节（1/4px 精度）。因此本 ADR 里「同屏 50 人 / 分散 150 人」的绝对数字
> 不再成立，闸门逻辑与水位的**结构**不变，只是同一台机器能装下的人明显变多。

## 决策

1. **同连接进程内排队（方案 A）**：`C2S_HELLO` 之后不再直接入世界，先经 `AdmissionController` 裁决；排队者保留在 `sockets` 表里，但**不进 `world`、不进 AOI**，因此零广播、零同步带宽，只每秒收一条 16 字节位次快照。
2. **三维水位取最大**：`max(带宽水位, 人数水位, Tick 水位)`。带宽是 `Transport.send` 唯一收口处的实测字节（50ms 环形桶、1.15s 窗口），不用人数估算——只有实测才能区分「同屏走动」与「分散挂机」。
3. **滞回 + AIMD + 熔断**：0.85 关闸、0.65 重开（单阈值会让排队屏在临界点闪烁）；容量每稳定 30s 加 2，持续越界按 25% 收缩且最多每 10s 一次，下限 10；Tick p95 连续 3 次达到 2 倍预算才熔断。容量收缩只由带宽/人数这种持续型指标驱动，Tick 瞬时尖刺交给熔断计数。
4. **放行限速**：每 Tick 最多放 2 人（约 40/s）。闸门一开就放几十人，会重演「同秒涌入导致百毫秒级长帧」的已知问题。
5. **队列上限随容量推导**：`clamp(容量 × 2, 50, 1000)`，AIMD 收缩时队列上限一起收紧，超出立即拒绝而不是无限堆积。
6. **掉线立即释放**位次，不做保位。协议里仍保留 `ticket` 字段，只用于日志串联，以及未来分片时替换 `AdmissionStore` 实现的接缝。
7. **一键回退**：`GAME_QUEUE_ENABLED=0` 回到「满了才拒」的旧行为，`shared-types` 的新 opcode 保留（旧客户端会忽略未知包）。

## 被否决的方案

| 方案 | 收益 | 代价 | 否决理由 |
|---|---|---|---|
| B：HTTP 票据 + 网关准入 | 可跨实例统一排队 | 需要 Redis/网关状态，打破「零持久化单进程」，多一个故障点 | 单实例下收益为零 |
| C：nginx `limit_conn` / 维护页 | 一行配置 | 无位次、无 ETA、非 FIFO，用户只看到 503 白屏 | 体验不成立 |

## 后果

- 正面：过载从「随机断线」变成「有解释的排队」；带宽成为可观测、可标定的量；容量跟着真实负载走，不需要人工调人数上限。
- 负面：排队者仍占一条 WebSocket 连接（几十 KB 级别）；多实例后只能按实例各自排队；AIMD 会带来容量抖动，需靠滞回与收缩间隔压住。
- 回滚成本：低。关开关即回到旧行为，无数据结构迁移、无协议下线。

## 复核信号

- 队列长期超过 50 人或平均等待超过 2 分钟 → 加带宽或按房间分线，而不是继续调阈值。
- 需要跨实例统一排队 → 把 `AdmissionStore` 换成 Redis 实现，`S2C_QUEUE_STATUS` 布局不变。
- 单机在线超过 300 人，或 Tick p95 持续超过 12ms → 与 ADR-0001 的复核线联动，评估分片。
- 水位的主导维度长期是 `Players` 而不是 `Bandwidth` → 说明去脏已经生效、带宽不再是瓶颈，
  该调 `GAME_MAX_ONLINE` 或评估分片，而不是继续加带宽（详见 ADR-0043）。
- 需要「排队保位」「防占坑」→ 引入 ticket 保位窗口（协议字段已就位）。
