# ADR-0083：P2P 互动走统一总线，玩法实现插件化处理器

- 状态：已采纳
- 日期：2026-11-15
- 关联：[ADR-0082](0082-niubi-coin-economy.md)（赌注与托管）、
  [ADR-0003](0003-aoi-grid.md)（视野距离口径）、[ADR-0073](0073-vent-ring-three-player-arena.md)（擂台独立战斗域）

## 背景

玩家之间的互动（挑战、打赏、道具）是同一类问题：**两个在线玩家 + 一次有超时的确认**。
如果每种玩法各自写一套邀请、倒计时、退款与忙碌状态，会出现：

- 玩家同时收到两个邀请，接受第一个后第二个永远卡在「等待回应」；
- 对局中途掉线，赌注留在托管里没人退；
- 新增玩法要改协议、改前端、改断线清理，三处都容易漏。

因此需要一个总线负责「邀请 → 托管 → 对局 → 结算 / 退款」，
把玩法本身隔离成可替换的处理器。

## 决策

### 1. 两段状态，一个忙碌真相

- `PendingInvite`：15 秒 TTL，`from / to / gameType / wager / extra / expiresAt`。
- `ActiveMatch`：赌注已冻结，`a / b / startedAt / endsAt / resolved / data`。
- `Player.busyMatchId` 与 `Player.pendingInviteId` 是「忙碌」的唯一真相；
  任何退出路径（拒绝、超时、取消、掉线、硬超时）都必须同时清空这两个字段。
  前端不用自己维护「我是不是在局中」，只读服务端下发。

### 2. 邀请在服务端二次裁决

客户端只发意图，服务端校验：目标在线且是真人、双方不忙、`gameType` 已注册、
赌注 `0..5000`、发起方余额足够、距离 ≤ 400px（与 AOI 视野同一口径）、
待处理邀请与活跃对局各有上限（32）。任何一条失败都回 `S2C_P2P_INVITE_RESULT` 并附原因码。

帮助文案与按钮禁用只是体验，**不作为安全边界**。

### 3. 处理器接口是插件点

```ts
interface ChallengeHandler {
  gameType: number;
  name: string;
  durationMs: number;
  onStart?(match, ctx): void;
  onInput?(match, player, payload, ctx): void;
  onTick(match, ctx): void;
  onCancel?(match, reason, ctx): void;
}
```

本阶段只注册 `gameType = 1` 的「牛马掰头」占位处理器：接受后由服务端延时裁决，
赢家拿走两份赌注。未来玩法替换这个处理器即可，总线、协议、前端都不用改。
`ctx.random()` 可注入，测试用固定序列验证胜负两条结算路径。

### 4. 赌注是托管，不是扣款

接受时双方各冻结 `wager`（`freezeEscrow`），`S2C_WALLET_SYNC` 立刻把余额变化推给两端。
结算时 `settleEscrow(winner, loser, wager*2)`；平局 / 取消 / 超时则双方 `refundEscrow`。
`resolved` 标志保证一局最多结算一次。

### 5. 断线与硬超时优先于玩法结果

- 掉线：邀请作废；进行中的对局按「对手掉线」判负结算，对手拿走赌注，双方忙碌态清空。
- 处理器忘记在 `endsAt` 收尾：`endsAt + 5s` 强制退款，宁可没有赢家，也不锁死玩家。
- Tick 空表早退，稳态零开销；只有活跃对局时线性增长。

### 6. 打赏 / 道具共用同一套限频

邀请、打赏、用道具、商店购买共用 `lastP2PAt` 的 500ms 闸门。
打赏只发生在真人之间（NPC 无钱包）；道具先扣库存再上效果，效果上限用 `max(now, 已有截止) + 时长`。

## 后果

- 正面：
  - 拒绝 / 超时 / 断线三条退款路径共用同一段清理代码，测试可以逐条覆盖；
  - 新玩法只需实现接口并注册，不动协议与 UI；
  - 邀请包与对局包全部定长 / 可解析，畸形包在 guard 层被丢弃。
- 负面：
  - 对局状态在服务端内存，重启即丢失；重启时所有人断线，对局按掉线收尾；
  - 占位玩法没有真实输入，`onInput` 目前未被协议触发；
  - 前端要同时处理「邀请结果」与「对局结束」两类收尾，不能只监听一个。

## 复核信号

- [ ] 需要 3 人以上或组队玩法 → 总线要从 1v1 扩展为队伍模型。
- [ ] 需要观战 / 回放 → 对局状态要落盘或转为可重放事件流。
- [ ] 出现跨局持久战绩或排名 → 需要与 ADR-0081 的落盘范围重新划界。
- [ ] 玩家利用掉线判负刷币 → 需要按设备冷却或延迟结算。

## 验证

- 服务端单测覆盖：邀请成功 / 忙碌 / 超距 / 余额不足、拒绝、超时、接受后结算、掉线退款、
  处理器硬超时兜底。
- 协议：`packages/shared-types/src/__tests__/economy-protocol.test.ts` 覆盖邀请 / 回应 / 通知 /
  结果 / 对局包的小端往返。
- 手工：两个浏览器窗口互相邀请，验证 15 秒浮窗、接受后钱包冻结、结算到账、
  关闭其中一个窗口后另一侧收到掉线结算。
