# ADR-0043：多园区部署——Web 单源 + 1…N 座独立 game-server

- 状态：已采纳
- 日期：2026-11-11
- 关联：ADR-0004（服务端零持久化）、ADR-0009（准入与排队）、ADR-0034（浏览器会话快照）、ADR-0038（有存档的访客直达园区）
- 部署手册：[`docs/deploy-multi-park.md`](../deploy-multi-park.md)（1 台 / 2 台 / N 台）

## 背景

园区是单实例部署。上限不是算力，是出口：

| 场景 | Tick p95 | 预算 |
|---|---|---|
| 60 人在线 | 2.03 ms | 25 ms（用掉 8%） |
| 200 人全同屏 | 6.49 ms | 25 ms（用掉 26%） |

真正卡住人数的是 `GAME_MAX_EGRESS_KBPS`（默认 320 KB/s，对应 3Mbps 机型）。要再装人只有一条路：多一台机器的出口。

这一次扩容时手上有两台规格不同的机器（下表是**当时的具体机型，仅作示例**，
通用结论见「决策」与「后果」中的公式）：

| | 主站机器 | 第二座园区 |
|---|---|---|
| CPU / 内存 | 2 核 / 4G | 4 核 / 4G |
| 公网带宽 | 5 Mbps | 3 Mbps |

需求是玩家在捏完人之后自己选进哪一座，并记住这次选择；进园之后还能换。
方案必须同时满足「只有一台机器时照常可用」与「以后再加第三、第四座时不用重做架构」。

## 决策

### 1. 一座园区 = 一个独立 game-server 进程，之间没有任何连接

ADR-0004 规定世界只活在进程内存里，昵称、外观、落点全部在浏览器侧。这条约束在多园区下变成结构性红利：**N 座园区天然是 N 座互不相干的世界，不需要分片协议、跨服同步、路由表或一致性窗口**。

也因此，园区数量是一个纯配置项：加一座只是再加一个进程与 `GAME_PARKS` 里的一条记录，
不是一次架构变更。只有一座时这套结构退化成零配置的单机形态（未配置 `GAME_PARKS`
即合成 `main`），所以「先上一台、以后再加」是同一条路径，不需要两次改造。

### 2. Web 只部署一份，其余每一座园区各用独立子域名直连

Web（Next.js）只留在一台机器上，其余每台机器各跑一个 game-server；浏览器用
`wss://<park-domain>/ws` **直接**连到对应的机器。

两个约束把方案挤到了这一个交点：

- **存档按 origin 隔离**。`niuma:profile:v2`、`niuma:park:v1` 都在 localStorage 里，若第二座园区是独立站点，A 域捏的牛到 B 域就是陌生人——直接违背「捏完人再选园区」。
- **不能反代**。若把 B 挂在 A 的 nginx 下（`/ws-b` → B:3001），B 的每一帧同步包都要穿过 A 的出口。A 的 320 KB/s 预算仍是全站瓶颈，等于没扩容，反而双倍占用 A。

### 3. 园区列表的唯一真相在服务端，客户端只持有 parkId

`GAME_PARKS`（JSON 数组）由 `apps/web/lib/park.server.ts` 在服务端读取，通过 Server Component 的 props 下发。客户端存档里只有 `{"id":"b"}`，**没有 URL**。

原因不是洁癖：`?park=` 与 localStorage 都是用户可改的。白名单翻译把「改存档」的后果限制成「回落到第一个园区」，而不是「连到任意地址」。同时它让园区列表成为运行时配置——加一台服只重启 Web，不重新构建（`NEXT_PUBLIC_*` 是编译期内联的，做不到这点）。

### 4. `/enter` 是独立页，不是 `/play` 里的模态

`GameViewport` 挂载即在 effect 里建会话（`GameViewport.tsx`），插一个「未连接态」等于把连接生命周期判断塞进渲染层；两张卡片各带在线/水位/延迟，移动端模态也放不下。

单园区时 `/enter` 直接 `redirect` 到 `/play`：单机部署看到的行为与改造前完全一致。

### 5. 入场前探活，首选不可达时自动顶替

`PlayShell` 在挂载游戏外壳之前先问一次目标园区的 `/health`：

- 只配一座园区 → 不探活，直接进；
- 首选可达 → 立即进，不等其它园区返回（进场只多一次往返）；
- 首选不可达 → 用其它园区里第一个可达的顶替，并改写 `niuma:park:v1`；
- 全部不可达 → 仍然进首选，让界面显示「连接中断，正在重连」，而不是把人挡在一张点不动的卡片前。

探活走浏览器直连各服 `/health`（服务端已带 `access-control-allow-origin: *`），一次请求同时拿到在线人数与「玩家 → 该园区」的真实往返。由 Web 服务端代理测出来的是 A → B 的延迟，跟玩家的体感不是一回事。

### 6. 落点按园区隔离，但不升快照版本

`niuma:session:v1` 增加可选字段 `park`；`resumeForPark()` 在 `park !== 当前园区` 时返回 `undefined`，角色从新园区门口开始。

不升 `v` 是刻意的：升版本会让所有老玩家的落点一起失效，而这里只需要让「换园区」这一种情况失效。没有 `park` 字段的老存档按「不匹配」处理。

### 7. 部署角色参数化

`deploy/jenkins-deploy.sh` 新增 `DEPLOY_ROLE=all|web|game`。主站机器用 `all`（或只跑 Web 时用 `web`），
每一台游戏服机器用 `game`：跳过 Next 构建与 Web 目录切换，只装 Bun 与游戏服。加第 N 座就是再跑一次。

## 被拒方案

| 方案 | 否决原因 |
|---|---|
| 同域名路径反代（`/ws-b` → B） | 流量穿过 A，出口瓶颈没解除，等于没扩容 |
| 每台机器都完整部署、各自独立域名 | localStorage 不同源，捏人存档不互通；且每台都要付一份 Next 的内存与构建峰值，挤掉游戏服预算 |
| 单机加带宽 / 单机起两个进程 | 出口仍是同一条线，玩家数不变；纯属多一个空世界 |
| 用 Redis / 中央注册表同步园区状态 | 违反 ADR-0004 的零持久化；各园区之间没有共享状态可同步 |
| 园区列表走 `NEXT_PUBLIC_*` | 编译期内联，加一台服要重新构建 |

## 后果

- 正面：整站容量等于各园区出口预算之和。按 `人均 5–8 KB/s` 估算，本次两台（400 + 300 KB/s）
  约为 90–115 人，对比单机 60 人上限；想再往上就是加机器，靠的是真实出口带宽，不是压缩画质或降低 Tick。
- 正面：每座园区的故障域完全独立，任意一台挂掉不影响其它园区的在线玩家，只是选园页上少一张可用卡片。
- 正面：回滚只动配置——`GAME_PARKS` 删到只剩想要的那几项并重启 Web，规模立刻缩回，代码不动。
- 负面：Web 仍是单点。Web 挂掉时所有园区都进不去。这是既有风险而非本次新增；真要解决得在另一台机器上再跑一份 Web 并让同域名 DNS 兜底，但那要多付 768 MB 内存，且两份 Web 要同步部署。
- 负面：非主站的游戏服机器多核基本闲置。这是出口带宽决定的，不是配置失误——在那类机器上多开园区不会增加一个玩家。
- 负面：`/health` 从「运维接口」变成「面向浏览器的公开接口」，容量与负载对外可见。信息价值低（本来就在公开页面上），但 nginx 必须限制只有 `/health` 放开 CORS。
- 负面：多了一个本地 key `niuma:park:v1`，以及一个可为空的快照字段。

## 回滚

1. 配置回滚（首选，30 天内随时可做）：`GAME_PARKS` 删到只剩想保留的那几项，重启 Web。
   只剩一项时 `/enter` 自动 307 到 `/play`；一项都不留时 `loadParks()` 合成 `main`，
   回到零配置的单机形态。代码不动。
2. 代码回滚：`CreatorShell` 的 `router.push('/enter')` 改回 `/play`，`auto-enter` 去掉 park 分支即可恢复旧路径；存档里多出来的 `park` 字段会被忽略。

## 复核信号

- 单园区在线持续超过 100 人，或出口水位长期 >80%：该加第三座园区，而不是继续调 `GAME_MAX_ONLINE`。
- Web 进程因内存反复重启：考虑把 Web 拆到独立机器或前置 CDN，而不是压缩游戏服预算。
- 出现「跨园区保持座位 / 身份 / 好友」的需求：这会推翻 ADR-0004，必须单独立项，不要顺手加数据库。
- 选园页的「身份不符」状态频繁出现：说明 `GAME_PARK_ID` 与 `GAME_PARKS` 的 id 对不上，属于部署事故而非产品问题。
