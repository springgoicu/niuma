# ADR-0043：静止不广播，同步条目压到 6 字节

- 状态：已采纳
- 日期：2026-11-11
- 关联：修订 [ADR-0009](0009-admission-queue.md) 的容量推导与复核信号；延续 [ADR-0003](0003-aoi-grid.md) 的「只发差量」思路

## 背景

ADR-0009 把下行成本写成「观察者 × 视野内实体数」，但漏了一个前提：**视野内所有人都算移动实体**。

客户端从入场起就以 20Hz 无条件上传移动包（`session.ts` 的 `sendMove` 不看有没有变），
服务端 `applyMove` 也无条件 `player.dirty = true`。于是哪怕 60 个人全坐在工位上发呆，
每个 Tick 仍然会给每人发一包含 59 条增量的同步包——广播成本与「有没有变化」完全无关。

这个产品的设定恰恰是「大部分时间在工位上坐着」，所以这笔开销是纯浪费：

| 场景（60 人，同一片区域） | 单客户端下行 | 全网出口 |
|---|---|---|
| 全员走动 | 8.42 KB/s | ≈ 495 KB/s |
| 全员坐班不动 | 8.42 KB/s | ≈ 495 KB/s |

一张 5Mbps（≈625 KB/s，扣开销后按 530 KB/s）的机器在 85% 水位关闸，实际只能承 60 人左右。

## 决策

### 1. 服务端：三元组不变就不置 dirty

`Player` 记录**上一次真正广播出去**的量化坐标与 state（`lastBroadcastQx/Qy/State`，初始 -1）。
`applyMove` 只做比较，`runTick` 在 `transport.send` 之后回写基准：

```
量化坐标变了 或 state 变了 → dirty = true，进入本 Tick 的广播
否则                        → 什么都不发
```

基准必须回写在「发送之后」：用「上一帧算出来的值」做基准，会让没发出去的变化被吞掉。
座位吸附（sit / stand / lie）仍无条件置 dirty——它确实改变坐标与姿态，且频率极低。

### 2. 客户端：变化即发 + 250ms 保活

`shouldSendMove` 是纯函数（`lib/game/move-send.ts`）：

- 三元组变了 → 按 20Hz 上限放行（`MOVE_SEND_INTERVAL_MS = 50`）
- 三元组没变 → 降到 4Hz 保活（`MOVE_IDLE_INTERVAL_MS = 250`）
- 判定基准同样是「上次真正发出去的值」，攒着没发的变化不会丢

**叠加位的结束必须立刻发**：叫唤 / 跳 / 挥手在本地到期后由 `expireLocalOverlays` 清位，
而远端的 `applyOverlayBit` 只认包里的位，没有自己的过期计时器。所以每帧都要重算 state 再比较，
漏了这一包远端会永久循环播放。

### 3. 速度窗口封顶

上行变稀疏后，「站 10 秒再走」会在服务端留下一个巨大的 `now - lastMoveAt`，
`allowed = MOVE_SPEED × elapsed × 1.25 + 3` 会跟着放大到 2000px，等于白送一次瞬移。
窗口封顶 `MAX_WINDOW_MS = 250`（5 个 Tick）：单包最多放行 ≈55px，既吸收抖动丢包又压住瞬移。

### 4. 同步条目 7 → 6 字节

48 bit 的位表：

```
bit  0..9   id        (10 bit)
bit 10..24  x @1/4px  (15 bit)
bit 25..39  y @1/4px  (15 bit)
bit 40..47  state     ( 8 bit，与 packState 一致)
```

**为什么必须降精度**：6 字节扣掉 state 的 8 位只剩 40 位，1/8px 下 x/y 各要 16 位
（8192px × 8 = 65536），留给 id 的只剩 8 位，装不下 1023 个实体；用岛屿偏移基址也不行，
南北跨度 33696 个单位已经超过 15 bit 的 32767。改成 1/4px 后 15 位正好覆盖 8192px，
位置误差 ≤0.25px（世界放大 1.5 倍后屏幕上 ≤0.375px），肉眼不可见。
解码时左移一位还原成 1/8px 单位，`dequantizeCoord` 与插值环完全不用改。

连带收窄：`MAX_ENTITIES` 1024 → 1023，`World.nextId` 回绕点 `0xfffe` → `0x3ff`。
准入容量远低于此，无实际影响。

### 5. 格式协商：HELLO 声明、WELCOME 回告

- 客户端在 HELLO 尾部追加 `[0xfd][format]`（沿用 0xff 状态段 / 0xfe 在线段的魔数惯例）。
- 服务端按每个连接各自的格式编码（`syncWriter` 本来就是每人一份），旧客户端继续收 7 字节。
- 服务端在 WELCOME 尾部追加一个格式字节，客户端据此解析。

**不按包长自适应**：截断的 7 字节条目恰好等于一条 6 字节条目（count=1、payload=6），
猜错不会报错，只会把垃圾字节读成坐标。格式是连接级契约，由服务端一次说清。

### 6. Tick 懒写包头

`runTick` 原先对每个玩家每 Tick 都 `reset()` + 写 7 字节包头。
改成首条条目到来时才写：静止人群整 Tick 不碰发送缓冲。

## 被否决的方案

| 方案 | 收益 | 代价 | 否决理由 |
|---|---|---|---|
| 按包长自适应条目格式 | 省一个协商字段 | 截断包有歧义 | 会把垃圾字节静默读成坐标，协议错误被推迟到更难查的地方 |
| 降 Tick 频率到 10Hz | 直接砍半带宽 | 走路明显变粘 | 手感是这产品的核心，优先砍无用流量而不是砍同步率 |
| 位置增量编码 | 再省 2~3 字节/条 | 需要绝对值兜底与状态机 | 去脏之后条目只来自真正在动的人，收益不足以换复杂度 |
| 合并多 Tick 发包 | 减少包数 | 增加延迟 | 包数不是瓶颈，字节数才是 |

## 后果

- 正面：坐班场景的下行从「与走动同价」变成接近 0；同样一条 5M 线路可承载的在线人数显著上升
  （见 ADR-0009 修订后的推导）。
- 负面：
  - 协议出现两种条目格式，客户端与服务端必须能互相识别；旧标签页靠能力协商自动走 7 字节。
  - 位置精度从 1/8px 降到 1/4px，同步条目与入场包之间有 ≤0.125px 的差，插值后不可见。
  - 去脏后带宽水位下降，AIMD 会把容量涨到 `GAME_MAX_ONLINE`，瓶颈会从带宽转到人数/CPU 维度。
    这是预期行为，`/health` 的 `admission.dominant` 会从 Bandwidth 变成 Players。
- 回滚成本：低。客户端不声明能力段即全体回到 7 字节；去脏与上行节流各自独立，
  回退 `markIfChanged` 与 `shouldSendMove` 不影响协议。

## 实测（Windows，机器人客户端与服务器同机，60 人）

| 场景 | 格式 | 单客户端下行 |
|---|---|---|
| 全员走动 | 旧 7 字节 | 8.42 KB/s（与改动前基线一致，验证压测口径没变） |
| 全员走动 | 新 6 字节 | 7.15 KB/s（−15%） |
| 全员坐班静止 | 新 6 字节 | 0.38 KB/s（其中大头是入场补发的 3540 个 spawn，稳态同步流量 ≈0.1 KB/s） |

压测命令见 README，「全员坐班」是本次新增的 `BENCH_IDLE=1` 模式。

## 复核信号

- 出现「远端叫唤 / 挥手停不下来」→ 先查叠加位到期那一包有没有被上行节流挡住。
- 出现「别人停在原地不动」→ 查 `lastBroadcast*` 是否在发送前就被回写。
- 需要 id 超过 1023 或把精度提回 1/8px → 升格式号（HELLO/WELCOME 各加一个值），不要原地改位表。
- 单机在线超过 `GAME_MAX_ONLINE` 且 `dominant` 长期是 Players → 带宽已经不是瓶颈，
  该评估分片或多实例（ADR-0001 复核线）。
