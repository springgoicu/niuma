# ADR-0011：外观扩到 32 字节，背包槽改发型，颜色按属性拆槽

- 状态：已采纳
- 日期：2026-10-30
- 推翻：ADR-0007 的「字节只换语义不换长度」与 ADR-0004 中的「20 字节外观」描述；ADR-0007 的部位迁移结论仍然有效。

## 背景

1. **背包槽读不出来**：ADR-0007 把配件迁到头顶 / 眼线 / 颈线之后，`[18]` 仍留给背包（`laptop` / `briefcase`）。
   64 网格、头径 17 的比例下，背包被躯干整块挡住，四个朝向都只剩一点边；侧视时背包还和尾巴抢同一块轮廓。
2. **颜色只有 5 个**：`body / pattern / hoof / eyes / extra`。口鼻靠借 `body` 染色，尾巴是 `body` 图层的一部分，
   头饰 / 眼镜 / 颈饰的图标把配色烘死在像素里。需求是「每个属性都能改颜色」，五个槽位无法表达。
3. **协议空间已经用满**：20 字节里 `[19]` 是唯一保留位，塞不下 6 个 `u16` 颜色。

## 决策

### 1. 外观定长 32 字节（一次性破协议）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 1 | species |
| 1–22 | 22 | 11 × u16 RGB565：body / pattern / hoof / eyes / extra / snout / tail / headwear / eyewear / neckwear / hairstyle |
| 23–26 | 4 | patternId / snoutId / extraId（角或鬃）/ tailId |
| 27–30 | 4 | headwear / eyewear / neckwear / hairstyle 目录索引 |
| 31 | 1 | reserved |

颜色顺序由 `APPEARANCE_COLOR_KEYS` 一处定义，编解码按数组下标循环，不再逐槽写死偏移。
hello / spawn / set-appearance / appearance-broadcast 四个包直接内嵌外观，长度常量自动生效；
服务端只做透传与钳制，**业务代码无需改动**。单包 +12 字节，200 人同屏的最坏下行仍远低于带宽预算。

### 2. 背包槽改发型

`BACK_IDS` → `HAIR_IDS = ['none','buzz','bangs','ponytail','afro','slick']`，`cosmetics.backItem` → `hairstyle`，
字节编号仍是 `[30]`。旧档的 1 / 2 会落到寸头 / 齐刘海，而不是随机一件。
发型是四向独立构图（马尾、爆炸头、大背头在背面与侧面各有造型），朝左由生成器镜像朝右。

### 3. 配件灰度化

`cosmetics.ts` 的 `Icon` 从写 RGB 改为只写明度四档（本体 255 / 阴影 208 / 深部 150 / 描边 52），
生成器输出灰度 PNG，客户端 `Sprite.tint` 染色。与 ADR-0002 的调色板替换同一条路线：
换色只改 tint，不重建纹理，也不额外打断合批。

### 4. 尾巴独立图层

`palette.ts` 新增 `tail` 层与 `Tail / TailShade / TailOutline` 槽位；`drawTail` 改写 tail 槽。
整帧描边仍然只出一次，之后做一次**描边归属改写**：四邻接里只有 tail 像素的描边改写成 `TailOutline`，
尾巴的轮廓就不会被主体色染跑。`LAYERS` 里 `tail` 排在 `body` 之前（尾巴始终在身后）。
`body / bodyLight` 因此不再随 `tailId` 分变体，图集少两张 PNG。

### 5. 客户端层序与锚点

`tail → body → pattern → bodyLight → hair → headwear → hoof → extra → eyes → eyeLight → eyewear → snout → neckwear`。
发型排在 headwear 之前，戴帽自然压住头发；锚点沿用 `landmarksOf().headTop` 再下移 1px，
让 20×20 的发块咬住颅骨——浮在头顶会读成一顶假发。

## 备选方案

| 方案 | 结论 | 理由 |
|---|---|---|
| A. 保住 20 字节，配件颜色由现有 5 色派生 | 否 | 「每个属性都能改色」直接落空；尾巴、口鼻也没有自己的槽位 |
| B. 只扩 1 字节，用 `[19]` 加一个色槽 | 否 | 1 字节装不下 RGB565，且 6 个属性仍然不够分配 |
| C. 配件保留烘焙多色，只给「主色」染色（accent 保色） | 否 | 图标与叠层翻倍（每件配件 2 张 × 4 向），20×20 下金链、薄荷标只有 2–3 像素，保色换不来可读性 |
| D. 尾巴继续留在 body 层，只让尾巴跟随主体色 | 否 | 与「全部属性独立着色」的需求冲突 |
| **E. 32 字节 + 灰度配件 + 尾巴分层（采纳）** | 是 | 一次把「槽位语义」「配色粒度」「渲染方式」三件事都摆正；新增属性时只要加一个颜色键和一层灰度图 |

## 后果

- 正面：11 个色槽各自独立、即时生效；发型在四向与坐躺帧都有可读造型；配件换色零纹理重建；
  新增一个属性只需「加颜色键 → 画灰度图 → 加锚点」三步。
- 负面：
  - 破协议。同一串字节在旧客户端里会被解错，必须前后端同版本发布；`sessionStorage` 里的旧草稿
    会丢掉 `backItem` 并回落到默认发型与默认新色（属于免费迁移，不是保留旧搭配）。
  - 帽子上的点缀色、单眼镜的金链不再保色，只靠明度四档区分材质。
  - 每帧最多多两个 sprite（tail 与 hair），单包 +12 字节。
- 回滚成本：中。需同时回退 `APPEARANCE_BYTES`、编解码偏移、生成器版本与客户端层序，并重跑 `pnpm assets`；
  服务端不含布局知识，回滚时只需要跟着换依赖版本。灰度过后的配件图无法与新协议混用，
  因为 manifest 与 `sprite-layout.generated.ts` 的版本号必须一致，客户端会直接报错而不是画错。

## 复核信号

- 改外观字段时，先看 `APPEARANCE_COLOR_KEYS` 与 `SLOT_TABLE` 是否同步；偏移是推导值，不要再写魔数。
- 新增配件只能写四档明度，不要写 RGB：一旦混入彩色像素，染色会跟着色相跑偏。
- 尾巴出现「描边颜色和尾巴不一致」时，先检查 `px.retagOutline(S.Outline, 'tail', S.TailOutline)` 是否被后续绘制覆盖。
- 发型如果看起来像帽子，优先怀疑锚点（应为 `headTop + 1`）与发块底边行号，而不是继续加细节。
